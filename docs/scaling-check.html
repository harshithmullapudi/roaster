Scaling check · Roster

One process, two seconds, ten connections

Roster is well-built for the size it is aimed at, and three specific decisions cap it hard. The fan-out layer already scales; the supervisor does not, and it lives inside the web server. This is a read of the code as it stands on this branch — where the load comes from, what saturates first, and what it costs to lift each ceiling.

Verdict

Capacity is set by concurrent agent sessions, not by users or messages. Each live session is a 2-second polling loop inside the Next.js process.

Comfortable today 5–15

concurrent live sessions, one org, ≤25 members, ≤100 channels. This is the shape the code was written for and it will feel fast.

First thing that breaks ~30–50

concurrent sessions, as written. The token-exchange half of that pair is now gone and the pool is wider, so this has moved up — by how much is unmeasured, and the number above is the one that was reasoned about, not a new claim.

Hard wall 1 instance

A second container cannot be added at all. Session state and uploaded files both live in process memory and on local disk.

Landed since this was written

The changes that lift a ceiling without anyone noticing — no UI change, no behaviour change, no deployment change.

  • Superset JWTs are cached per credential — keyed by a hash of the stored ciphertext and held until a minute before expiry, with concurrent callers sharing one mint and failures never cached. Rotating a key invalidates it immediately. Removes one HTTP round-trip and two queries from every tick of every session.
  • Eight correlated subqueries per row became two batched lookups — reply counts, last-reply times, replier names and the lead session now resolve in one grouped query and one DISTINCT ON across the whole result set, the same way delegation state already did.
  • The pool is sized deliberately — 20 rather than pg's implicit 10, with a connection timeout so a starved pool fails instead of hanging forever, and a generous statement timeout so one slow query cannot hold a connection indefinitely. Both overridable by env.
  • threads (organization_id, last_activity_at desc) is indexed — the filter behind the live-thread query that runs on every page load.
  • Migrations take an advisory lock — and run on their own pool, so overlapping boots serialize rather than race, and a long migration is not subject to the runtime statement timeout.

Verified against Postgres with a 33-assertion equivalence harness over the rewritten queries (including lead-session ordering and deleted-reply exclusion), three concurrent migrators, and eight new unit tests on the token cache. Full suite green.

Where the load actually comes from

Not requests. A single agent session generates more sustained traffic than a browsing user does, and it generates it whether anyone is watching or not.

pollOnce fires every 2 seconds for each live session. On every tick it reads the session row, then calls hostConnection, which does two more queries, decrypts the stored Superset key, and mints a fresh JWT over HTTP — there is no cache. Then it pulls up to 32 KB of transcript and lists the agent bindings. When the progress line has changed (the normal case while an agent is working) it writes the session row and republishes thread state, which costs four more queries and two Centrifugo publishes.

Capacity model

Polling cost only — page loads, message sends and terminal streams sit on top of these numbers and share the same ten connections.

Concurrent live sessions Queries / s Outbound HTTP / s JWT mints / s Transcript ingress State
5 ~18 ~13 2.5 80 KB/s Comfortable.
20 ~70 ~50 10 320 KB/s Page latency starts to jitter behind the thread-list queries.
50 ~175 ~125 25 800 KB/s Pool queuing is visible; 25 token exchanges/s from one IP is throttle territory.
100 ~350 ~250 50 1.6 MB/s Not reachable on the current shape without the Tier 0 fixes.

Postgres itself is nowhere near its limit at 175 queries/s. What saturates is the pool of ten, and the trigger is head-of-line blocking: the thread-list queries build eight correlated subqueries per row and sort on one of them, so a handful of slow ones hold connections while every 2-second poller queues behind them.

Ceilings, ranked

Ordered by how much they cap the system, not by how hard they are to fix. The first three are the ones that decide the architecture.

  1. The app cannot run two instancesblocker

    hosts, watches, byTerminal and pendingSteers are module-level Maps. ensureStarted() adopts every session in starting or running into the local process, and it is triggered by a page render. Two instances means both poll every session and both can call finish() — which double-posts the agent's reply (the dedupe only compares against the immediately-previous agent message) and settles the same delegation twice, steering the parent thread twice.

    packages/api/src/services/sessions/supervisor.ts:114–118, 1423–1454 · apps/web/src/app/[slug]/[channelSlug]/page.tsx:55

  2. A JWT is minted from scratch on every poll tickfixed

    hostConnection runs two queries, an AES-GCM decrypt, and a live HTTP round-trip to api.superset.sh/api/auth/token — every 2 seconds, per session, and again inside finish, interrupt, resume and cancelSession. At 50 sessions that is 25 token exchanges per second from a single IP. Caching by host key until expiry removes a third of all polling traffic for about twenty lines of code.

    packages/api/src/services/sessions/connection.ts:11–43 · packages/superset/src/client.ts:26

  3. Attachments live on the container filesystemblocker

    Uploads are written with writeFile under UPLOADS_DIR and read back into memory in full to be streamed through the Node process. That needs a single-attach volume, which reinforces the one-instance limit, and it puts up to 10 MB per download through the same event loop that renders pages. No CDN, no range requests, no presigned URLs.

    packages/api/src/services/attachments.ts:37, 96–118, 165–168 · apps/web/src/app/api/files/[id]/route.ts

  4. Mention resolution rescans the whole org per message

    notifyForMessage calls listMentionableChannels (every channel in the org) and listMentionableMembers (every member) just to find @handles — on every message, including every agent progress message the supervisor writes. sendMessage does the same pair again when watch is off. Two full org scans per message, twice.

    packages/api/src/services/notifications.ts:110–141 · packages/api/src/services/messages.ts:323–349 · packages/api/src/services/channels.ts:34

  5. Eight correlated subqueries per thread rowfixed

    replyCount, lastReplyAt and replierNames (itself a four-table join), plus four lead-session lookups and startedAt, are computed per row — up to 100 rows for a channel, 200 for the inbox. Worse, the ordering is desc(startedAtSql): sorting on a correlated subquery means Postgres must evaluate it for every candidate row before it can sort, so no index can help. This is the query class that holds pool connections.

    packages/api/src/services/sessions/queries.ts:70–108, 227–247, 258–311

  6. No index on threads.organization_idfixed

    The table is indexed on root_message_id, project_id and (project_id, last_activity_at) — but listLiveThreads, listInboxThreads and the notification scope all filter on organization_id. listLiveThreads runs on every page load with a correlated EXISTS per row. Fine at ten thousand threads, not at a million.

    packages/db/src/schema/roster.ts:227–234 · packages/api/src/services/sessions/queries.ts:331–355

  7. threadDetail loads every message in the thread

    No limit, no paging. Agent progress messages accumulate, and the whole set is serialized through superjson into the RSC payload whenever someone opens a thread. A long-running thread gets slower to open forever.

    packages/api/src/services/sessions/queries.ts:530–548

  8. Every message serializes on one row

    allocateSeq does UPDATE projects SET last_seq = last_seq + 1, taking a row lock on the channel for every message written. That caps per-channel write rate and makes projects a hot-update table — one dead tuple per message, on a row that every page load also reads.

    packages/api/src/services/channels.ts:335–344

  9. Realtime publishes are fire-and-forget

    publish has a 2-second timeout; failures are logged and swallowed with no retry or outbox. Clients only reconcile on subscribe or resubscribe, so a three-second Centrifugo hiccup silently drops messages until someone reloads. Correctness of the feed currently depends on the hop never failing.

    packages/api/src/services/centrifugo.ts:52–97 · apps/web/src/hooks/use-channel-realtime.ts

  10. Two or three queries before any handler runs

    better-auth has no cookieCache, so every request does a session lookup, and memberProcedure then does a membership lookup. Multiplied across 13–17 queries per channel page, this is a meaningful slice of the pool. The built-in rate limiter is in-memory, so it resets on deploy and coordinates with nothing.

    packages/auth/src/server.ts:47–50 · packages/api/src/trpc.ts:22–49

  11. Migrations race on bootfixed

    instrumentation.register() runs migrateToLatest() in every booting instance with no advisory lock. Harmless with one container; a rolling redeploy that briefly overlaps two is a schema race.

    apps/web/src/instrumentation.ts

  12. Terminal streams are proxied through the app

    Each open terminal holds an SSE response plus an outbound WebSocket in the web process, base64-encoding every output chunk on the way through. Cheap individually; at a few hundred concurrent it makes the single instance a bandwidth bottleneck it does not need to be — the browser could hold a scoped token and talk to the relay directly.

    apps/web/src/app/api/terminals/stream/route.ts

What is already built right

These are the decisions that mean the fixes above are additive rather than a rewrite.

Fan-out is delegated, not homegrown

Centrifugo carries the WebSocket fan-out with short-lived HMAC subscription tokens per channel. That layer is already horizontal and needs nothing.

Notifications are subscriber-scoped

Fan-out is bounded by thread subscribers rather than broadcast to the org, and a partial unique index on (member_id, message_id) makes delivery idempotent.

Agent recursion is bounded

Depth capped at 3, cycles rejected by walking the ancestor chain, and one open delegation per parent enforced by a partial unique index. No runaway fan-out is possible.

Pagination is keyset, not offset

Messages page by seq; notifications use a proper (created_at, id) tuple cursor. Both stay flat as the tables grow.

Writes are idempotent at the edge

A unique index on (project_id, client_id) plus onConflictDoNothing makes a retried send safe, which is what lets the client be aggressive.

The host already pushes lifecycle

Start / Stop / Failed arrive over a WebSocket per host. The polling loop is a belt-and-braces layer on top of a push channel that already exists — which is exactly why it can be backed off.

Fix ladder

Each tier is independently shippable and each one buys roughly an order of magnitude. Nothing in Tier 0 changes the architecture.

Tier 0 — buy 5× without changing anything 4 of 6 landed

  1. done Cache the Superset JWT per credential until expiry minus a minute. Removes one HTTP call and two queries from every tick of every session.
  2. done Set max on the pg Pool explicitly — it was the pg default of 10, which was the system's invisible ceiling. Now 20, with a connection timeout and a generous statement_timeout.
  3. done Index threads (organization_id, last_activity_at desc).
  4. Enable better-auth cookieCache to drop a query from every single request.
  5. Bound threadDetail to the latest N messages with paging backwards.
  6. Resolve mentions with a targeted query by handle instead of listing every channel and member in the org — or cache those two lists per org for a few seconds.

Tier 1 — buy 10× and unlock a second instance ~4 days left

  1. Move attachments to object storage with presigned URLs. Removes file bytes from the Node process and removes the volume that pins the app to one container.
  2. done Kill the eight-subqueries-per-row pattern. Taken the no-drift route: batch the counters and the lead session across the result set rather than denormalizing them onto threads. Same numbers, no backfill, nothing that can fall out of sync. Denormalizing is still available later if the batched queries become the bottleneck.
  3. Back the poll off adaptively. Lifecycle already arrives by push. Poll at 2 s only while the transcript is actually changing; decay to 10–30 s when it is not. On a typical session this alone cuts polling traffic by most of it.

Tier 2 — become horizontal ~2–3 weeks

  1. Lift the supervisor out of the web process into a dedicated worker, with session ownership claimed in Postgres — an owner_id and claimed_at heartbeat on thread_sessions, taken with SELECT … FOR UPDATE SKIP LOCKED. The web tier then becomes stateless and scales out, and the worker can be sharded by host key.
  2. Give realtime an outbox. Persist the event, then publish, so a Centrifugo blip is a delay rather than a loss, and let clients resync from a seq instead of refetching the window.
  3. done Take a pg_advisory_lock around migrations. They also run on a dedicated pool now, so a long migration is not cut short by the runtime statement timeout.

After Tier 0 and 1, one instance should carry roughly 150–250 concurrent sessions and a few hundred active users. After Tier 2 the ceiling stops being Roster and becomes Postgres write throughput and the agent hosts themselves.

Method and caveats

This is a static read of the code on this branch — schema, services, the supervisor, the realtime hooks and the deployment files — with no load test and no production telemetry behind it. Query counts are exact (traced by hand through the call paths). The throughput numbers are arithmetic on those counts and on the constants in supervisor.ts; they are a model, accurate to the right order of magnitude, not measurements. The session-count thresholds are the least certain figures here: where exactly the pool starts queuing depends on Postgres round-trip time and on how large the thread tables have grown, and the Superset token-exchange limit is set by that service, not by this code. Measure before trusting the boundary; trust the ranking.
