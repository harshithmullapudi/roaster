Roster · design · v5 · 25 Sep 2026

Agents are people

One directory, one @, a type column. Connecting a folder adds its agent to the team; a channel can have as many more as it wants; each has a brief you edit where you edit anyone's profile. This is the version that deletes code instead of adding a table.

The move

Agents become rows in members with type = 'agent' and a channel. Humans keep type = 'human' and have none.

Why it's right

The unique namespace already exists — members_org_agent_name_idx. The collision problem from the last draft evaporates.

What it deletes

rejectPersonHandle(), the computed-handle helpers, and a three-table join that reconstructs who spoke on every message read.

The trap

members.user_id is notNull, and deleting a member nulls its messages' author. Ephemeral must mean hidden, never deleted.

Part one

One directory, one @

Today people and agents are different kinds of thing whose handles differ by a suffix. That is the source of every naming problem in the last four drafts.

members.agent_name currently does two jobs. It is the person's mention handle — findMemberByHandle() matches @harshith straight against the column — and it is the first half of every channel agent handle, since channelAgentIdentity() joins it to the channel slug via projects.addedByMemberId (channels.ts:188). So @harshith is a person and @harshith-superset is an agent, and roster ask carries a whole function whose only job is to apologise for the difference (rejectPersonHandle, delegations.ts:50).

Now — two namespaces, one grammar

members.agent_name → @harshitha person members.agent_name + projects.slugcomputed at read time → @harshith-superset

Neither knows about the other, both are mentioned as [a-z0-9-]+, and whoever happened to click connect decides what the agent is called.

Proposed — one directory

membersone table · one org-unique name · one @ type: human → @harshithno channel type: agent → @supersetchannel: #superset · added when the folder was type: agent → @superset-pmsame channel · created on demand · editable brief

Uniqueness is one index, already in the schema. Nothing can collide because nothing computes a name any more.

That index is members_org_agent_name_idx, unique on (organization_id, agent_name) (auth.ts:132). It is already exactly the constraint we need — in the last draft I was proposing a new agents table to get it. Putting agents in members means the namespace question is answered by code that already shipped.

What the row looks like

Column Human Agent

Part two

What this deletes

The reason to prefer it over a separate table: three special cases stop existing rather than gaining a branch.

  1. The apology function

    rejectPersonHandle() exists only because @harshith and @harshith-superset are different kinds of thing (delegations.ts:50–70). When an agent is a person, asking one is just asking a member who happens to be an agent. The whole function goes, along with the error copy it carries.

  2. Reconstructing who spoke, on every message

    Agent messages currently store author_member_id = null and recover identity through two aliased joins — message → agent channel → that channel's owner member → their agent_name — then compute a display name in TypeScript (message-columns.ts:31–37, :91–96). When the agent is a member, author_member_id is simply set. Both aliases, the join condition and the computation all disappear, and two agents of one channel render as two speakers with no extra column.

  3. Handles computed at read time

    agentHandle() and agentDisplay() (agent-identity.ts) build a string from a person's name and a channel slug every time anything is displayed, and resolveAgentHandle() enumerates every visible channel and string-matches to reverse it (channels.ts:177). Stored names make both a single indexed lookup. Keep agentHandle() exactly long enough to seed the migration, then delete it.

Migration is a backfill, not a break. For every channel, insert one agent member whose agent_name is today's computed ${owner}-${slug} — so @harshith-superset keeps resolving verbatim — then backfill author_member_id on existing agent messages from agent_channel_id. Renaming to @superset is something a human does afterwards, never automatic.

Part three

Ephemeral or permanent

Both, as you said — but "ephemeral" has to mean hidden, because deleting the row corrupts the transcript.

The foreign key decides this. messages.author_member_id is references(members.id, { onDelete: "set null" }) (roster.ts:101). Delete an ephemeral agent when its thread ends and every message it wrote becomes authorless — the history stops being able to say who said what. So an ephemeral agent is one that is archived and delisted, not one that is removed.

Ephemeral

roster agents create pm --ephemeralor created implicitly by an ask

└─ while the thread runs

mentionable, speaks, attributed normally

└─ thread completes

archived: delisted, not mentionable, row keptold messages still say who wrote them

Frees the name for reuse. Good for a one-off second opinion.

Permanent

roster agents create pmthe default

└─ lives on the channel

listed in the team section, brief editable@superset-pm forever

└─ later threads

asked again, same brief, accumulating definition

The thing you described: called once, remembered, @-able after.

Since both are the same row with a different flag, there is no reason to pick one. Default to permanent — a team that names a PM usually wants it tomorrow too — and let --ephemeral be the deliberate choice for a throwaway. An agent created implicitly by an ask should be permanent but marked auto-created, so the team section can offer to archive the ones nobody ever edited or asked twice.

Part four

The CLI

ask already takes a handle, so most of this is new only in what resolves. 

# who can I talk to — humans and agents, since they are one directory
roster agents
roster agents --channel superset          # just this channel's

# make one. permanent by default, on this channel, with a brief
roster agents create pm --brief "Own the spec. Ask about scope, not syntax."
roster agents create reviewer --ephemeral # gone from the directory when the thread ends

# ask takes an agent name — no new verb, no --here flag
roster ask superset-pm "scope the onboarding change"
roster ask design-core "review the empty states"

And the worktree rule needs no flag, because it follows from who you asked:

You ask Worktree Why
An agent on your own channel Yours. The same supersetWorkspaceId the calling session is in, as a second session beside it. It shares your channel, so it shares your folder. There is nowhere else it could run.
An agent on another channel A fresh one from that channel's repo, on that channel's machine. Today's behaviour, untouched. It has its own folder. Running it in yours would be the surprising thing.

Which also settles the trust question raised two drafts ago: nothing belonging to another channel ever executes against your checkout or on your machine.

Part five

What the code needs

The identity work is mostly subtraction. The session work is five items, three of which are bugs already waiting for a shared worktree.

Identity

Today Becomes Where
members.user_id is notNull Nullable, with a check that a human has a user and an agent has a channel. The one migration with teeth. auth.ts:116
Agent messages carry agent_channel_id, author null author_member_id set like anyone else; the column and its joins retire after backfill message-columns.ts:31
Every member query assumes human Filter on type. listMentionableMembers, member lists, notification fan-out — miss one and an agent gets emailed, or shows up in a list of people. channels.ts:107 and callers
thread_sessions unique on (thread_id, project_id) (thread_id, agent_member_id), so two agents of one channel stop colliding roster.ts:286
delegations.target_channel_id target_member_id; the self-target rejection becomes "not yourself" rather than "not your channel" delegations.ts:110

Sessions

  1. Session start must be able to reuse a worktree

    startSessionRow() calls createWorkspace() unconditionally (supervisor.ts:1007); it needs to accept an existing id. Nothing upstream blocks this — resume() already runs an agent against an existing supersetWorkspaceId at :1268, and the relay's createTerminal and listTerminals are per-workspace and plural by design.

  2. The host must come from the session, not the project

    hostConnection() derives the routing key from the session's project (connection.ts:87). The seam already exists: thread_sessions.superset_host_key is stored per session, jwtForMember({ memberId, hostKey }) exists, and reapThread already prefers session.supersetHostKey ?? connection.hostKey (supervisor.ts:1511).

  3. Reaping will delete the shared worktree twice

    reapThread() loops every session calling deleteWorkspace for each (supervisor.ts:1497). With a shared workspace the second call fails, hits continue, never sets workspaceReapedAt — and assertReaped() then throws "1 workspace outlived the reap". Dedupe by workspace id. The one place a shared worktree breaks something that works today.

  4. A human reply only ever reaches the main session

    steer({ threadId }) resolves mainSession() and nothing else (supervisor.ts:1317). Fine as a default, but @superset-pm in a thread message has to route to that session.

  5. Settling is keyed on a child thread that won't exist

    settleDelegationFor({ childThreadId }) returns the answer to the caller (delegations.ts:300). A same-channel ask has no child thread and needs none — delegations.child_thread_id is already nullable (roster.ts:466). Key it on the delegation id.

Already free. thread_sessions.role has carried a delegate value since the table was written and nothing has ever set it (roster.ts:244). And keeping delegation's blocking semantics means only one agent executes in the worktree at a time — they hand the branch back and forth, so no file leases, no locks, no merge. The turn-taking that made roster ask feel restrictive is exactly the concurrency control a shared checkout needs.

Part six

The nits, and where they stand

Twelve settled by this design, six still yours. Say the word on any of the settled ones and they reopen.

Nit Call Status
Where agents live members with a type column, not a separate table. The unique index we need is already on it. settled
Handle uniqueness members_org_agent_name_idx, unchanged. People and agents share one namespace, which is what makes one @ correct. settled
Naming the channel's agent A real stored name, set when the folder is added, editable after. No longer derived from whoever clicked connect. settled
Migration Backfill one agent member per channel using today's computed handle, then backfill message authors. Nothing breaks; renaming is manual. settled
Humans without channels project_id null for humans, set for agents. The general team stays channel-less. settled
Where the brief is edited The team section, on the agent's profile — same place you edit a person. Not channel settings. settled
Ephemeral means what Archived and delisted, never deleted. author_member_id is set null on delete, so removal would orphan the transcript. settled
Default lifetime Permanent. --ephemeral is the deliberate exception. settled
Which worktree Decided by who you ask, not a flag. Own channel → yours; another channel → its own. settled
Concurrency in a shared folder Blocking turn-taking. One agent executing at a time, so no leases and no locks. settled
Agent credentials None, ever. A session runs on the key of whoever triggered it, which is already how runAsMemberId works. settled
Agent permissions role = 'member', so no invite, remove, role-change or channel-update capability. Make it explicit in the insert, not incidental to the default. settled
Do agents count as seats There is no billing code in the repo yet, so nothing inflates today. Define the count as type = 'human' now, while it costs one line, rather than discovering it during pricing. yours
Where the brief is stored Database only, or mirrored to the repo as .roster/agents/pm.md. The repo version is reviewed like code and travels with the branch; the database version can be fixed by someone who cannot merge. Real trade. yours
Turn cap and stop condition Suggest six exchanges plus a termination phrase, counted on threads.turn_count, which is already incremented on every steer. Arbitrary until we watch one run. yours
Do agents appear in the sidebar member list Mentionable regardless — the question is whether they are listed beside humans or kept to the team section and autocomplete. Three agents across twenty channels is sixty entries in a list of people. yours
Can another channel ask your agent It falls out for free: roster ask superset-pm from #roster would get a fresh worktree of superset's repo. Correct, but decide it is wanted before it ships by accident. yours
Seeded agents Ship pm, reviewer, qa with written default briefs, or leave every name free text. Seeds make the feature legible; free text stops us guessing what teams want. yours

Appendix

What everyone else does

The field has converged on worktree-per-agent. Nobody ships agents with identities that persist between sessions, which is the part this design is actually about.

Tool Same folder? How they coordinate
Conductor Yes, explicitly — "multiple chats in one workspace when the agents need the same branch and current code state, such as one session implementing while another reviews". Nothing built in; shared context lives in committed docs or a .context directory. Closest to this design, minus the identities.
Cursor 3.x No — worktree per agent on its own branch; 3.2's /multitask fans subagents across isolated branches. Visibility only. Humans merge and resolve conflicts by hand.
Claude Code subagents Yes — they inherit the working directory. The parent is the only coordinator; shared contracts must be fixed before fan-out. Anonymous and per-session, which is what a Roster agent is not.
MCP Agent Mail Yes — built for it. Identities, inboxes, and advisory leases over globs — advisory because hard locks cause head-of-line blocking. We get the same safety from turn-taking instead.
AutoGen / CrewAI Not coding tools. The two schools: a moderator choosing the next speaker at runtime, versus fixed roles in a fixed sequence. Our supervisor is already a fixed-sequence moderator.
