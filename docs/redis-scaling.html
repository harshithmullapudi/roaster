Roster · scaling

Where Redis moves Roster's ceiling

Ten places Redis buys real headroom, ranked by payoff, each measured against what the code does today. Plus five places it would be the wrong answer — which matters more, because the tempting misuses here are the ones that quietly trade correctness for throughput.

The shape of the problem

Roster is one process by construction, and three separate things hold it there.

All background work lives inside the Next.js server. The supervisor keeps five Maps and a Set in module scope (supervisor.ts:145–157), holds one WebSocket per memberId@hostKey, and runs one setInterval per live session (supervisor.ts:687). A page render boots it: page.tsx:55 calls void ensureStarted().

So a deploy drops every live watch until something re-adopts it, nothing recurring can be scheduled because no timer outlives a request, and a second copy of the process would be actively harmful — a steer queued in one copy's pendingSteers is invisible to the other, and both would race to finish the same session.

Worth separating the three constraints, because only one of them is Redis's to solve. Coordination state is the supervisor's in-memory maps — Redis's job, and most of this page. Durable truth is Postgres, and it should stay there; the last section explains why that is a correctness requirement rather than a preference. Large bytes are attachments on a local volume (attachments.ts:38), which is what docs/deploying.md:30 means by “it rules out replicas” — object storage, not Redis, and the one ceiling nothing here lifts.

1 — 4  The ceiling itself

These four are the difference between one process and several.

01Session ownership leases

Today
watches, hosts and byTerminal are process-local maps. Only the process holding a machine's events socket can route the Start, Stop, Failed and PermissionRequest events that arrive on it (supervisor.ts:411).
With Redis
A lease per memberId@hostKey — the existing linkKey — held with SET NX PX and renewed on a heartbeat. Sessions inherit their owner from their link, so one lease covers every session on a machine and lifecycle routing stays a local map lookup.
Unlocks
A worker tier that can run more than one instance, and crash recovery that is continuous rather than boot-only: lease expiry is the crash signal, so a sweep can adopt orphaned sessions instead of waiting for someone to load a page.
Cost
The lease has a documented failure window — see the last section. It must be treated as coordination, never as the thing that makes concurrency safe.

02A scheduler that outlives a request

Today
There is no scheduler. The only recurring timers are the supervisor's per-session poll and its reconnect backoff, and both die with the process.
With Redis
BullMQ job schedulers hold cron state in Redis, so a schedule survives a deploy and only one occurrence of a slot can ever be produced.
Unlocks
Scheduled tasks — a cron expression that posts a message into a channel so the agent opens a thread on it — plus every maintenance sweep Roster currently has nowhere to put: adopting orphaned sessions, reaping stale worktrees, expiring invite links.
Cost
A slot that passes with no worker running fires once, late, and intermediate slots are dropped silently. That is observed behaviour rather than a documented contract, so the version wants pinning and firings want recording in Postgres.

03Durable command and steer queues

Today
pendingSteers (supervisor.ts:154) holds steer text in memory. Restart the process and queued steers are gone; the user is told only because the code remembers to say so.
With Redis
A list per session for steers, and a list per link for commands, with a pub/sub channel used purely as a low-latency doorbell. The list is the source of truth, so a dropped notification costs latency and never a command.
Unlocks
Commands addressed to a machine whose owner is mid-restart simply wait. It also gives the blocking operations — cancel, retry, reap — a reply channel, which they need because their callers render the result rather than fire and forget.
Cost
Redis pub/sub is at-most-once, so the periodic drain is the correctness mechanism and the doorbell is the optimization. Getting that backwards produces a system that works until it doesn't.

04Terminal fan-out

Today
api/terminals/stream/route.ts:39 opens a relay WebSocket per viewer. Three people watching one agent work is three sockets to the same terminal, each with its own SSE stream, all pinned to the web process.
With Redis
One holder per terminal, discovered through the same lease primitive as session links, publishing frames to a Redis channel that every viewer's SSE stream subscribes to.
Unlocks
Socket count scales with active terminals rather than with viewers — the difference between a demo and a standup where everyone opens the same thread.
Cost
Terminal output is high-frequency, so this is the one use here with real throughput considerations. Worth measuring before assuming the fan-out is cheaper than the duplicate sockets.

5 — 10  Work taken off the hot path

Individually small. Together they are most of what a request currently spends its time on.

05Centrifugo's Redis engine

Today
docker/centrifugo/config.json declares no engine, so Centrifugo runs the in-memory one, holding 300 messages and 30 minutes of history per namespace in process memory.
With Redis
The Redis engine, which is a configuration change rather than application code.
Unlocks
More than one Centrifugo node, and history that survives a restart. Note the three namespaces set force_recovery: true — a promise of recovery that the in-memory engine silently cannot keep across a restart today.
Cost
Lowest-effort item on this page, and the only one that needs no application change at all.

06API-key last-used writes

Today
api-keys.ts:79 writes lastUsedAt on every successful key verification. Every roster invocation by every agent — each channel read, each task status change — is one Postgres UPDATE whose only purpose is a timestamp nobody reads in real time.
With Redis
Record last-used in Redis on the hot path and flush to Postgres periodically, or on a scheduled sweep.
Unlocks
Removes a write from the single most frequent authenticated path in the system, which is also the path that scales with agent activity rather than human activity.
Cost
Last-used becomes approximate, by the flush interval. For a “when was this key last seen” column in settings, that is the right trade.

07Channel-visibility cache

Today
listChannels runs on three hot paths: the channel list itself, channel visibility (channels.ts:95), and listTasks (tasks.ts:72), which needs it to work out which channels a member may see before it can filter tasks at all.
With Redis
Cache the visible-channel-id set per organization, member and role, with a short TTL and explicit invalidation on membership and channel changes.
Unlocks
Task and channel listing stop paying for the same fan-out query repeatedly, and the saving grows with channel count rather than staying flat.
Cost
This one is an authorization input, so staleness is a security property, not just a freshness one. Invalidate on write and keep the TTL short enough that a missed invalidation self-heals fast.

08Cross-process cache invalidation

Today
The Superset JWT cache is a process-local map (jwt-cache.ts:30), and forgetSupersetCredentials() (connection.ts:18) clears only the one in the process that called it. Its trigger lives in the web process.
With Redis
A pub/sub invalidation channel. Each process keeps its fast local cache and drops entries when told to.
Unlocks
Closes a real gap rather than a slow one: once a worker exists, a member who reconnects Superset leaves that worker holding a JWT minted from the old key for as long as its lifetime allows. If the old key was revoked, that is a window of failing sessions nobody asked for.
Cost
Invalidate, don't centralize. Moving the JWTs themselves into Redis would put bearer credentials at rest in a cache to save a round trip that is already cheap.

09Unread counters

Today
unreadNotificationCount (notifications.ts:495) is an aggregate count() behind the inbox badge, run per member per poll.
With Redis
A counter per member, incremented where notifications are already written and cleared on read.
Unlocks
A badge that costs a GET instead of an aggregate, on one of the few queries every open tab runs regardless of what the user is doing.
Cost
Must be rebuildable from Postgres on a miss, and must be treated as a cache rather than the count. A drifted counter should be self-correcting, not a support ticket.

10Backpressure toward hosts

Today
Host reconnect backoff is per-process state: attempts on a HostLink, capped by MAX_ATTEMPTS (supervisor.ts:390). There is no rate limit toward the Superset API or the relay.
With Redis
A shared token bucket per host and per member, so backoff and rate limits are properties of the fleet rather than of one process.
Unlocks
Retry pressure on an offline machine stops multiplying by worker count. This is the item whose absence only hurts after item 1 succeeds, which is exactly the kind of thing worth writing down before it bites.
Cost
Adds a Redis round trip to a path that currently has none. Applies to reconnects and mint calls, not to steady-state polling.

Where Redis is the wrong answer

The tempting misuses, and what breaks. This section matters more than the ranked list.

Not as the arbiter of session state

A SET NX PX lease loses mutual exclusion on failover, and on any pause longer than its TTL two holders both believe they own it. Redis's own documentation says so and prescribes fencing tokens. So every state transition that matters needs a conditional UPDATE … WHERE <expected state> RETURNING in Postgres, and the lease is only there to stop duplicate sockets and duplicate polling. Build it the other way round and the failure mode is not a slow page — it is two workers finishing the same session, a canceled overwritten by a completed, and duplicate agent messages in a thread.

Not for message sequence numbers

allocateSeq (channels.ts:335) is a single atomic UPDATE … SET last_seq = last_seq + 1 RETURNING, which does serialize inserts per channel on one row lock. A Redis INCR would be faster and would be a bad trade: messages_project_seq_idx is unique, so a counter that is ever lost or rolled back produces hard insert failures rather than a slow path. The contention is per channel, and a channel is a conversation. This is not the bottleneck it looks like.

Not for the poll loop

Turning each watch tick into a queued job spreads polling across workers, which sounds like the point. But lifecycle events only arrive on whoever holds the machine's socket, so ownership is required anyway, and a queue round trip per session per tick buys nothing for it. The setInterval belongs on the owning worker.

Not for attachment bytes

Attachments are the one thing genuinely pinning the web tier to a single instance, and they are a job for object storage. Blobs in Redis would trade a disk problem for a memory problem and would still need noeviction to be safe. Good news for the worker tier: attachmentsForMessages (attachments.ts:245) returns rows and URLs rather than bytes, so background work needs no volume at all.

Not as a second copy of the truth

Every cache above is reconstructible from Postgres, and that is the property to hold onto. The moment something exists only in Redis, its persistence configuration becomes a correctness dependency rather than an operational one — and a cache nobody can rebuild is a database with no backups.

What it costs to run

Requirements, not preferences.

Setting Value Why
maxmemory-policy noeviction Arbitrary eviction breaks queues and command lists. Not a tuning choice.
Persistence AOF A restart that loses a lease key can hand the same link to two owners.
Connections ~4 per worker Two for a queue worker, one dedicated subscriber, one producer. A subscribed connection cannot issue other commands.
Producer behaviour Fail fast Request-path producers should error rather than buffer while Redis is unreachable; workers should wait out the reconnect.
Availability Hard dependency Once ownership lives here, Redis down means no sessions start. It joins Postgres in the critical path.
